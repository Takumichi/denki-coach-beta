## 2. 何が起きていたか

### A. ブランチ運用がセッション固有名に固定されていた

旧 `CLAUDE.md` では、Claude Codeの作業ブランチとして `claude/denki-tantei-pro-status-ciombn` が固定されていた。

これは別セッション・別ブランチからClaude Codeを開いた場合、現在の作業ブランチと関係なく古いブランチへcommit/pushしようとする原因になる。

### 解決

恒久的なブランチ名固定を廃止。

今後は作業開始時に必ず:

```bash
git branch --show-current
```

で現在ブランチを確認し、ユーザーが明示承認した作業ブランチにだけcommit/pushする。

`main` への直接pushは明示承認がない限り行わない。

---

### B. Thought Partner Councilがプロジェクト文脈まで禁止していた

Skillの安全ルールで「現在のプロジェクト状態・履歴」を参照しないよう記載されていたため、機能・価格・事業判断など、プロジェクト固有の相談でも既存仕様を見ずに一般論だけで回答する危険があった。

### 解決

**非機密のプロジェクト文脈は参照可能**に修正。

一方で、以下は必要性がない限り参照・記載しない:

- 医療
- 福祉
- 家計
- カード情報
- 認証情報
- API Key / Secret
- その他のPRIVATE情報

つまり「プロジェクト固有の判断にはプロジェクト情報を使う」「個人の機密情報は混ぜない」という分離を徹底する。

---

### C. Research Intelligenceへの引き継ぎ先が存在しない環境があった

Skill内では外部確認が必要な場合に `Research Intelligence` へ渡すルールだったが、Claude Code側にそのSkillやコマンドが存在しない環境では処理が止まる。

### 解決

Research Intelligenceが利用可能なら連携する。

利用できない場合は、Claude Code自身が利用可能な一次情報・公式情報・リポジトリ内資料を使って検証し、確認できないものは「未確認」と明示するフォールバック運用にする。

存在しないSkillを前提に処理を止めない。

## 5. 今回のコミュニケーション上の学び

今回、ユーザー側ではGit/GitHubの英語用語である「merge」の意味が十分に共有されていなかった。

これは今後のClaude Code運用で重要な判断材料とする。

### 今後のルール

破壊的・公開影響のある操作の前には、技術用語だけで承認を求めない。

たとえば `merge` とだけ言わず、必ず日本語で:

> 「作業中の変更を正式版 `main` に合流し、公開版へ反映される状態にします」

のように、**操作結果まで平易に説明する**。

特に以下は日本語の意味を添える:

- merge = 作業内容を正式版へ合流
- commit = 変更を履歴として保存
- push = GitHubへ送信
- pull = GitHubの変更をPCへ取り込む
- branch = 本体とは分けた作業用の枝
- PR / Pull Request = 正式版へ入れる前の確認依頼
- deploy = 利用できる環境へ公開・反映

ユーザーが英語用語を理解している前提で重要操作を進めない。

## 6. マージ判断の標準手順

今後PRを `main` にマージする前に、Claude Codeは最低限以下を確認する。

1. PRの変更内容を日本語で要約する。
2. 未解決レビュー指摘を確認する。
3. 指摘を「アプリ本体」「開発運用」「資料」「セキュリティ」に分類する。
4. 公開版へ影響する重大問題があれば停止する。
5. 残る既知問題がある場合は、その影響と扱いを日本語で明示する。
6. ユーザーに「mainへ正式合流する」意味を説明する。
7. 明示承認後にのみmergeする。
8. merge後は `main` HEADとGitHub Pages / deploy状態を確認する。

急ぎの場合でもレビュー確認は省略しない。

---

## 7. Claude Codeへの判断原則

- 「誰のミスか」を探すより、再発しない仕組みに変える。
- ユーザーの言葉が技術用語と一致しない場合、意図を平易な日本語へ翻訳して確認する。
- 既知の不具合を黙って正式版に入れない。
- ただし、問題を領域ごとに切り分け、アプリ本体に影響しない問題まで理由なく開発停止させない。
- 正本（source of truth）を明確にする。
- 古い仮説と正式決定を混同しない。
- PRIVATE情報とプロジェクト情報を分離する。
- 外部送信、削除、購入、Secret変更、commit、push、merge、deploy、公開設定変更は、明示承認の範囲内だけ実施する。
